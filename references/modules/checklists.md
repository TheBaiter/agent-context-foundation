# Checklists Module

Read when the repository repeatedly needs specialized verification or closeout for a class of changes.

Create checklists only when they reduce omissions beyond what exact tests and project rules already provide.

A checklist should be narrow and evidence-based. Typical dimensions may include UI, API contracts, data changes, auth, deployment, dependencies, generated files, or migration work.

Every applicable checklist should end with:

- what was verified,
- what was intentionally not verified,
- remaining risk,
- whether durable knowledge changed.

Use `references/templates/checklists-index.md`.

Do not create a universal checklist catalog preemptively.
